# The Tower — правила работы с репозиторием

## Приоритет

- Делаем **The Tower**, а не новую версию p34t. Не предлагать и не начинать миграцию на p35t, общий рефакторинг или «подготовку фреймворка» без отдельного запроса.
- Сначала прочитать `docs/CODEBASE_BOUNDARIES.md`. Для конкретной задачи смотреть релевантный игровой код; защищённую инфраструктуру читать только настолько, насколько нужно для интеграции.
- Для работы над магазинным циклом прочитать `docs/SHOP_LOOP_V0.md`: там согласованные решения и следующие атомы, но не перечень уже реализованных фич.
- Развивать игру небольшими, проверяемыми шагами. Не добавлять абстракции, подсистемы и универсальные компоненты без текущей игровой потребности.
- Не менять существующее поведение p34t ради косметики, стиля, переименований или «чистоты архитектуры».

## Границы изменений

- Основная рабочая область: `src/app/scenes/game/**` и новые **игровые** модули внутри `src/app/`. Новые игровые UI-компоненты размещать здесь, не в библиотеке p34t.
- Защищённая зона по умолчанию: `src/system/**`, `src/components/**`, `src/utils/**`, `src/app/scenes/BaseScene.ts`, `src/app/scenes/boot/**`, `src/types/**`, `scripts/**`, `deploy/**`, а также конфигурация сборки. Не рефакторить и не исправлять попутно.
- Узкие точки интеграции: `src/index.ts` (регистрация сцен), `src/app/scenes/preload/Preload.ts` (загрузка ресурсов), `src/config/**`, `src/index.html`, `package.json`. Менять только конкретный параметр или подключение, нужные задаче; не переписывать окружающий код.
- Игровые ресурсы: `assets/raw/**` (исходники) и `assets/live/**` (ресурсы для запуска). `public/assets/**` — копия из `assets/live/**`; не редактировать вручную.
- Если задача действительно требует изменения защищённой зоны, **остановиться и согласовать** точные файлы и причину с пользователем. Не обходить границу через дублирование фреймворка.

## Формат разработки: только .patch

1. Источник истины — актуальный `master` репозитория `elkranio/The-Tower`. Перед подготовкой патча проверить текущий коммит и получить полные реальные файлы; не строить diff по обрывкам, старым версиям или воображаемому каркасу.
2. По умолчанию **не делать коммиты и не пушить изменения**. Выдавать пользователю скачиваемый `.patch`, который он проверяет и применяет локально.
3. Сразу после ссылки на патч дать **ровно две отдельные команды**, удобные для копирования: первая — `git apply --check <file.patch> && echo "Patch OK"`; вторая — `git apply <file.patch>`. Ошибки проверки должны быть видны; никаких `--quiet`, `--silent` и многословного `--verbose`.
4. Самостоятельно проверить патч на исходном состоянии: `git apply --check`, затем после пробного применения `git diff --check` и релевантные проверки кода. В ответе честно указать, что запускалось, а что нет.
5. Патчи узкие и атомарные. Не включать в них форматирование несвязанных файлов, случайные артефакты сборки, зависимости или правки p34t.
6. Если патч не применяется, **не предлагать force/3-way как стандартное решение**. Сначала сверить базовый коммит и пересобрать патч против актуального дерева.

## Контекст и передача работы

- `handoff.md` — краткая передача состояния **только когда она действительно нужна**: что сделано, текущий коммит/патч, проверки, что осталось, известные блокеры. На старте файл намеренно пуст.
- Не превращать `handoff.md` в длинный дневник или список гипотетических задач.
- Геймдизайнерские идеи не считать утверждёнными решениями без явного согласования с пользователем.
- Не запускать `npm run deploy`: текущий скрипт — старый FTP-деплой p34t, не инфраструктура релиза The Tower.
